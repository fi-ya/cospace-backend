# Authentication Workshop Notes

The updated project domain now includes `User.password`, which must contain a bcrypt hash and never plaintext. This database change is represented in `prisma/schema.prisma` and the additive Prisma migration at `prisma/migrations/20260928090000_add_user_password/migration.sql`.

## 1. Install Authentication Packages

These dependencies have already been installed on this branch. To reproduce the setup in a fresh checkout, run from the repository root:

```sh
npm install bcrypt jsonwebtoken
npm install -D @types/bcrypt @types/jsonwebtoken
```

`bcrypt` hashes and verifies passwords. `jsonwebtoken` signs and verifies JWTs. Keep both runtime packages and their TypeScript definitions in the appropriate dependency sections of `package.json`.

## 2. Configure the JWT Secret

Add a strong, unique secret to the ignored repository-root `.env`, alongside `DATABASE_URL`:

```dotenv
JWT_SECRET="replace-with-a-long-random-secret"
```

Generate a random value locally; do not use the placeholder above as a real secret. Do not commit `.env`, print the secret in logs, or use a fallback signing key. Add only the variable name with an empty or explanatory placeholder to `.env.example`.

The application must fail to start if `JWT_SECRET` is missing. `prisma.config.ts` also loads `.env` for Prisma CLI commands; application code must load environment variables before reading the secret.


# 3. Add authentication utilities
I chose 12 bcrypt salt rounds and a one-hour token expiry; adjust these if the workshop specifies different values. 
- hashPassword(password) and comparePassword(password, hash) using bcrypt.
- generateToken(user) and verifyToken(token) using jsonwebtoken.
- Required JWT_SECRET with no fallback. Tokens contain only userId and email, and expire after one hour.

# 4. Add Express middleware for authentication

The `requireAuth` middleware checks for a Bearer token in the `Authorization` header, verifies it using `verifyToken`, and attaches the decoded user payload to `req.user`. If the token is missing or invalid, it calls `next` with an `UnauthorizedError`.

Added requireAuth in requireAuth.ts. It accepts a Bearer token, verifies it, attaches the { userId, email } payload to req.user, and forwards an UnauthorizedError for missing, malformed, or invalid tokens.

Updated express.d.ts so req.user matches the verified JWT payload. TypeScript compilation, editor diagnostics, and git diff --check all pass.

The middleware is attached to booking write routes. Public booking reads remain unguarded.

# 5. Register and Login Endpoints

The draft auth flow is wired at `POST /auth/register` and `POST /auth/login`:

- Registration validates the employee fields, hashes the password with `hashPassword`, and stores the hash using `UserRepository`. The response contains a safe user profile and excludes the password hash.
- Login looks up the user by normalized email, compares the submitted password with the stored hash using `comparePassword`, and returns a JWT plus a safe user profile. Invalid email/password combinations return the same generic `401` response.
- A duplicate email is returned as a `400` error using the project's standard error middleware.
- Passwords must be at least 8 characters and no more than 72 UTF-8 bytes, matching bcrypt's input limit.
- `team_id` is optional and nullable at registration; when provided, it must reference a real team.

The User Prisma model requires `password String @db.VarChar(255)`. The repository accepts only a value already hashed by the controller. Never return the hash or log it.

## Add the Password Column

The `User` Prisma model now includes:

```prisma
password String @db.VarChar(255)
```

The field is required because every account created through registration must have a credential hash. Never add a default password or populate existing users with a fabricated hash. If the target database already contains users without passwords, a required-column migration will fail unless you first define a real password enrollment/reset process and backfill each account with a valid bcrypt hash. A clean development database can apply the migration without that backfill.

The migration adds the required column without a database default:

```sql
ALTER TABLE `users` ADD COLUMN `password` VARCHAR(255) NOT NULL;
```

### Why this migration is not generated by `migrate dev`

On the existing `cospace` database, `npx prisma migrate dev --create-only` reported drift in foreign-key and index names and offered to reset the database. Do not accept that reset. The migration should contain only the reviewed password-column change; do not fold unrelated constraint or index changes into it.

Before applying migrations in another environment, confirm it has the expected `0_init` baseline and CoSpace schema. A new, empty development database can apply the migration normally. For a populated database, follow the password-backfill plan first. If Prisma reports drift or proposes a reset, stop and investigate instead of resetting valuable data.

## 4. Apply and Verify the Migration

With `.env` targeting the intended development database, run:

```sh
npx prisma validate
npx prisma migrate status
npx prisma migrate deploy
npx prisma generate
npx prisma migrate status
npx tsc --noEmit
```

`migrate deploy` applies pending committed migrations without running the development shadow-database drift workflow. It does not reset the database. Confirm the migration is recorded and the `users.password` column exists. On a populated database, verify all existing user rows can satisfy the required non-null column before applying it. Do not use `migrate reset` to bypass drift.

## 5. Authentication Implementation Checklist

- Hash passwords on registration with `bcrypt.hash`; verify login credentials with `bcrypt.compare`. Never compare plaintext directly to a hash.
- Sign JWTs with the required `JWT_SECRET`; verify the bearer token before trusting its payload.
- Return only safe user fields. Never return the password hash from register or login responses.
- Attach the verified user identity to the request and derive booking `user_id` from that identity, not from a client-supplied ID.
- Protect write routes with authentication middleware while keeping public reads public, as required by the API design.
- Keep password, token, and personal data out of logs.

## Assumptions and Remaining Work

- The workshop did not specify registration response shape, password policy, or JWT lifetime. This draft assumes registration returns `201` with the safe user profile, passwords are at least 8 characters and at most 72 UTF-8 bytes, and JWTs expire after one hour.
- `requireAuth` protects booking write routes while booking reads remain public. Booking creation derives the owner from the verified `req.user.userId` claim rather than accepting `user_id` from the request body.
- Automated auth/API tests are not included yet. Add tests for hash storage, successful and failed login, duplicate emails, invalid/expired JWTs, password-hash omission from responses, and invalid optional `team_id` values.
- The fixed development `JWT_SECRET` must be replaced with a strong local secret in `.env`; never commit that file or use a fallback secret.

Before committing on `feature/api-authentication`, run `npx tsc --noEmit` and the available auth/API tests.

## Bind Bookings to the Authenticated User

In `booking.controller.ts`, take `req.user.userId` from the verified JWT payload and pass it to the service and repository. In Prisma, connect the booking's actual `user` relation with `user: { connect: { id: userId } }`. Do not accept `user_id` from the request body as the booking owner; the `Booking` model has a `user` relation, not a `createdBy` relation.
