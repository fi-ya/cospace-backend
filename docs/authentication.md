# Authentication Workshop Notes

The updated project domain now includes `User.password`, which must contain a bcrypt hash and never plaintext. This database change is represented in `prisma/schema.prisma` and the additive Prisma migration at `prisma/migrations/20260928090000_add_user_password/migration.sql`.

## 1. Install Authentication Packages

These dependencies have already been installed on this branch. To reproduce the setup in a fresh checkout, run from the repository root:

```sh
npm install bcrypt jsonwebtoken
npm install -D @types/bcrypt @types/jsonwebtoken
```

`bcrypt` hashes and verifies passwords. `jsonwebtoken` signs and verifies JWTs. Keep both runtime packages and their TypeScript definitions in the appropriate dependency sections of `package.json`.

## 2. Configure the JWT Secret

Add a strong, unique secret to the ignored repository-root `.env`, alongside `DATABASE_URL`:

```dotenv
JWT_SECRET="replace-with-a-long-random-secret"
```

Generate a random value locally; do not use the placeholder above as a real secret. Do not commit `.env`, print the secret in logs, or use a fallback signing key. Add only the variable name with an empty or explanatory placeholder to `.env.example`.

The application must fail to start if `JWT_SECRET` is missing. `prisma.config.ts` also loads `.env` for Prisma CLI commands; application code must load environment variables before reading the secret.

## 3. Add the Password Column

The `User` Prisma model now includes:

```prisma
password String? @db.VarChar(255)
```

It is nullable for this transition because existing employee rows have no password. Do not create a default password or populate old rows with a fabricated hash. New registration must always hash a supplied password with bcrypt before writing it. Existing users need a defined password setup/reset flow before the column can safely become required; after all rows have valid hashes, a later migration can make it non-null.

The migration is additive and preserves existing rows:

```sql
ALTER TABLE `users` ADD COLUMN `password` VARCHAR(255) NULL;
```

### Why this migration is not generated by `migrate dev`

The `0_init` migration is recorded as applied, but `npx prisma migrate dev --create-only` currently reports drift in existing foreign-key and index names and offers to reset the database. Do not accept that reset. The live-schema diff showed the password-column addition plus unrelated constraint/index changes, so the checked-in migration contains only the reviewed password-column statement. This keeps the migration scoped and avoids changing unrelated database constraints.

Before applying migrations in another environment, confirm it has the existing `0_init` baseline and the same CoSpace schema. If Prisma reports drift or proposes a reset, stop and investigate instead of resetting valuable data.

## 4. Apply and Verify the Migration

With `.env` targeting the intended development database, run:

```sh
npx prisma validate
npx prisma migrate status
npx prisma migrate deploy
npx prisma generate
npx prisma migrate status
npx tsc --noEmit
```

`migrate deploy` applies pending committed migrations without running the development shadow-database drift workflow. It does not reset the database. Confirm the migration is recorded and the `users.password` column exists before implementing registration or login. Do not use `migrate reset` to bypass drift.

## 5. Authentication Implementation Checklist

- Hash passwords on registration with `bcrypt.hash`; verify login credentials with `bcrypt.compare`. Never compare plaintext directly to a hash.
- Sign JWTs with the required `JWT_SECRET`; verify the bearer token before trusting its payload.
- Return only safe user fields. Never return the password hash from register or login responses.
- Attach the verified user identity to the request and derive booking `user_id` from that identity, not from a client-supplied ID.
- Protect write routes with authentication middleware while keeping public reads public, as required by the API design.
- Keep password, token, and personal data out of logs.
